# Security review — 20 September 2026

Local application review and automated verification, not an independent penetration test. Real Cloudflare policy/identity, remote resources and deployment remain unconfigured and unverified.

| Question                                                      | Finding and evidence                                                                                                                                                                                                                                        |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Can an unauthenticated user access `/admin`?               | No in tests: middleware returns 403 before owner content. Built-Worker checks agree. Real Access policy must gate exact and nested paths too.                                                                                                               |
| 2. Can unauthenticated requests directly mutate an admin API? | No in tested routes; authorization runs before writes. Tests inspect unchanged database state.                                                                                                                                                              |
| 3. Can a forged Cloudflare identity header authenticate?      | No: email/unsigned identity headers are ignored. Signed RS256 assertion required; forgery tests pass.                                                                                                                                                       |
| 4. Can a valid Access non-owner mutate content?               | No in tests: correctly signed non-owner is rejected by configured subject allowlist without changes.                                                                                                                                                        |
| 5. Can drafts leak through public endpoints?                  | Public queries use published pointers and omit private notes/edit IDs; relations/media are publication-filtered. HTML/API/graph/media transition tests pass.                                                                                                |
| 6. Can supplied Markdown execute JavaScript?                  | Raw HTML/images disabled; safe links and escaped JSX; hostile stored payload and strict CSP tests pass. HTTPS links still need editorial review.                                                                                                            |
| 7. Can uploads execute in the origin?                         | Server accepts narrow validated raster PNG only, strips metadata and serves correct MIME/nosniff/sandbox CSP. SVG, malformed and oversized payloads rejected. Decoder bugs remain a general residual risk.                                                  |
| 8. Can input cause SQL injection?                             | Bound values and fixed identifier allowlists. SQL payload remains data; schema and records remain intact in integration test.                                                                                                                               |
| 9. Can admin responses be publicly cached?                    | Browser and CDN no-store on admin/dynamic/media responses, including errors. Header tests pass; operator CDN overrides remain an external risk.                                                                                                             |
| 10. Are secrets in tracked files?                             | None found in credential-pattern/path scan or manual source review. Examples are placeholders and real identity/CSRF values use platform secrets. Heuristic scanning is not proof of absence.                                                               |
| 11. Are generated build files tracked?                        | No dependencies, builds, caches, databases, private config or AI state. Lockfile and reviewed migrations/snapshots are intentional source.                                                                                                                  |
| 12. Are source maps/debug endpoints exposing data?            | Source maps disabled and build scan checks them. Actual Worker returns 404 for source/environment/map paths; no debug route or runtime auth bypass.                                                                                                         |
| 13. Are dependency vulnerabilities known?                     | Patched lockfile audit reports zero known advisories on review date. Global esbuild override removes the obsolete Drizzle-loader copy. This result is not a future guarantee.                                                                               |
| 14. Does CSP match the application?                           | External scripts/styles, same-origin media and nonce JSON-LD; no unsafe-inline/eval or inline events. Desktop public flows worked without application CSP errors. Development injection can be blocked intentionally.                                       |
| 15. Can destructive actions happen accidentally?              | Separate publish action/confirmation, dirty-form blocking, typed slug for unpublish/delete, version checks, unpublish-before-delete, duplicate-submit prevention and retained revisions reduce risk. Deliberate owner actions still require review/backups. |

Real deployment must verify Access path matching and owner policy, issuer/audience/subject, session expiry/revocation, JWKS rotation, before-auth rate rules, R2 privacy, disabled alternate Worker URLs, live cache/CSP behavior, real devices and backup restoration. Application tests cannot certify account configuration. No unhackability or live-production claim is made.
